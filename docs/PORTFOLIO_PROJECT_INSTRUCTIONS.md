# PIUS 포트폴리오 제작 절차 (Claude용)

`[포트폴리오 등록]` 양식(docs/PORTFOLIO_INTAKE.md)이나 "포트폴리오 등록/추가/만들어줘" 요청을 받으면 이 절차를 **질문 없이 바로 시작**한다.
필수 정보는 프로젝트명과 자료 한 가지뿐이다. 나머지는 자료에서 찾고, 끝까지 확인되지 않는 것만 마지막에 묻는다.
완성 예시: `content/portfolio/fity/project.json`. 구조: `docs/PORTFOLIO_SCHEMA.md`.

## 절대 규칙
1. **새 페이지·컴포넌트를 만들지 않는다.** `content/portfolio/<slug>/project.json` + `images/`만 추가한다. 렌더러는 템플릿 개선 요청이 있을 때만 고친다.
2. **모르는 사실을 만들지 않는다.** 사용자 수·매출·성과 수치·출시일·기간·기술 스택·수행 범위·상태는 자료에 근거가 있을 때만 쓴다. 모르면 필드를 비우거나 `pending: true`(화면에 안 나옴).
3. **화면을 지어내지 않는다.** 받은 스크린샷이나 실제 데모 캡처만 쓴다. 다른 UI를 그리거나 없는 기능 화면을 만들지 않는다.
4. **외부 링크 금지** (서비스 URL·배포 주소·GitHub·Figma·테스트 서버·관리자 주소·QR). 검사에서 오류가 난다.
5. **개인정보** — 실명·연락처·주소·결제 내역·얼굴(실사용자)·내부 주소가 보이는 화면은 쓰지 않는다. 데모의 가짜 연락처처럼 실제처럼 보이는 것도 피한다.
6. **문구는 한·영·일을 함께.** ko 원본, en·ja는 자연스러운 현지 표현.
7. 같은 화면을 두 번 쓰지 않고, 같은 레이아웃·배경을 연달아 쓰지 않는다.
8. 배경은 중립색. `theme.accent`는 서비스 BI의 실제 색(브랜드·디자인 시스템 아티팩트나 데모 CSS 토큰에서 확인)만 쓴다.
9. **거래처(고객사) 공개 금지.** 거래처 이름·로고·상호·브랜드명·서비스명·담당자, 그리고 거래처를 특정할 수 있는 표현(예: 지역+업종 조합)은 어디에도 쓰지 않는다 — 제목·설명·slug·이미지 id·파일 이름·화면 속 글자와 로고 모두. 이름 대신 업종·성격으로 쓴다("여객 운송사", "기업 통근버스"). 거래처 이름은 `content/portfolio/_clients.txt`에 추가하면 검사에서 자동으로 막히고, 캡처 때 화면 글자에서 자동으로 가려진다. 이미지 속 로고·상호는 `--mask <css>`로 가리거나, 받은 이미지라면 가린 뒤에 쓴다.
9-1. **도식 툴로 그린 구조도·흐름도는 쓰지 않는다.** Mermaid·draw.io 같은 일반 다이어그램 툴 모양(노란 박스·화살표 선·기본 폰트)의 시스템 구조도·아키텍처도는 포트폴리오 이미지로 쓰지 않는다. 받은 자료에 있어도 넣지 않고, 구조 설명이 필요하면 글로 쓴다. 디자인된 업무 흐름 인포그래픽(MES·WMS 흐름 화면처럼 서비스 화면 톤으로 만든 것)은 예외.
10. **화면이 없어도 등록한다.** 스크린샷·데모가 전혀 없으면 `images: []`, `thumbnail: []`, `stack`(기술 이름)을 채워 글과 기술 스택만으로 공개한다. 카드·표지는 기술 스택 타이포그래피로 자동 대체된다. 화면이 생기면 이미지와 화면 블록만 추가한다.

## 공개 상태 정하기
- 기본은 `approved`(바로 공개). 거래처 이름을 모두 가렸으면 고객사 프로젝트도 공개 승인을 따로 묻지 않는다.
- 거래처를 가릴 수 없는 경우(화면 전체에 상호가 박혀 있는데 가릴 수 없음 등) → 그 화면을 빼거나, 빼면 성립하지 않을 때만 `review` + 마지막에 질문
- "비공개" → `private`
- 이주성(이 계정 주인)은 PIUS 개발팀장이다. 그의 개인 포트폴리오·경력 자료에 있는 프로젝트는 PIUS 실적으로 등록해도 된다(사용자 확인, 2026-11-05). 개인 연락처·개인 경력 수치(경력 연수, 프로덕트 수, 개인 기여도 %)는 옮기지 않는다.

## 순서 (요청 한 번에 끝까지)

**0. 준비** — 최신 `pius-work-vN-*.zip`을 새 폴더에 풀고 `npm ci`. 화면 확인용 폰트 설치(CLAUDE.md 참고).

**1. 자료 찾기** — 첨부 파일 → 이 프로젝트 파일·대화 → **사용자의 아티팩트 목록**(`list_artifacts`, 프로젝트명으로: 데모·디자인·BI·기획서·인수인계서) → 저장소(`list_repos`). 이주성 개인 포트폴리오(joosung.dev)의 원본 화면은 GitHub `appdevs-lee/portfolio`의 `assets/`에 있다(사이트 주소는 작업 환경에서 막혀 있어 저장소로 받는다). 인수인계서·기획서는 Docs 도구로 읽는다. 여기서 구분(자체/고객사 — 고객사면 거래처 이름을 `_clients.txt`에 먼저 추가), 수행 범위, 상태, 연도, 브랜드 색을 확인한다.

**2. 화면 확보** — 스크린샷이 있으면 그대로(WebP 권장). 없고 데모가 있으면:
- 데모 파일 받기: `list_files` → `read_file`(paths, 4MB·32개씩). 받은 파일은 summary의 sha256으로 원래 경로에 배치. 이미지가 많은 데모는 먼저 HTML만 받아 화면을 띄우고, 404 난 이미지만 골라 받는다.
- 캡처: `npm run portfolio:capture -- --slug <slug> --name <id> --url <데모 index.html> --preset mobile|desktop [--fill <css> <값>] [--click <텍스트>] [--eval <js>] [--close-dialogs]`
  - 모바일 1170×2532, PC 2880×1800 JPEG. 로그인·메뉴 이동은 --fill/--click, 데모 내부 라우터는 --eval.
  - 알림·권한 팝업은 --close-dialogs 또는 데모 상태값으로 끈다. 깨진 이미지가 보이는 화면은 쓰지 않는다.
- 고르는 기준: 대표 3장(카드·표지), 사용자 흐름 4~6장, 역할별 업무 화면 1~3장, 나머지 쇼케이스 2~4장.

**3. slug·카테고리** — slug는 영문 소문자(예: `abc-erp`). 카테고리: 사내 업무 → erp · 여러 사용자 그룹 → platform · 앱 화면 → mobile · 웹/관리자 → web · 결제·판매 중심 → commerce · 외부 시스템 연결 중심 → integration (복수 가능). 카테고리는 메인 Portfolio 숫자 타일에도 그대로 집계되므로, 앱이 있으면 mobile을 빠뜨리지 않는다.

**4. 데이터 작성** — `npm run portfolio:new -- <slug>`로 시작해 채운다.
- title, subtitle(20자 내외), summary(카드 한 문장), overview(2~3문장), cover.headline(두 줄), cover.sub
- 역할별 기능 → `services` / 고객 여정 → `userFlow` / 핵심 과제 3~4개 → `overview.goals`
- `order`: 기존 사이 값(10 단위). 대표로 크게 보일 것만 `featured: true`.
- 근거·남은 확인 사항은 `reviewNotes`(화면에 안 나옴)에 적는다.

**5. 블록 배치 (기본형, 자료에 맞게 빼고 더함)**
| 순서 | 블록 | 언제 |
|---|---|---|
| 1 | cover | 항상. 앱 3장 또는 웹 1장 + 앱 1장 |
| 2 | overview | 항상 |
| 3 | services | 사용자 역할이 2개 이상 |
| 4 | userFlow | 순서 있는 앱 화면 4장 이상 |
| 5 | textImage `imageRight` + light | 서비스의 대표 기능 1개 (폰 2장이면 나란히 크게) |
| 6 | textImage `full` + light | 대표 업무 웹 화면 (첫 장 크게, 나머지 아래) |
| 7 | textImage `imageLeft` + dark | 관리자·보조 웹 (PC 2장이면 겹쳐 배치) |
| 8 | screenShowcase `phones` + accent | 남은 앱 화면 2~4장 |
| 9 | scope | 항상 (확인된 항목만 보임) |
| 10 | statement | 항상 |
- ERP·관리자 중심이면 5~7을 PC 위주로, 앱 중심이면 4·8을 키운다. `featureGrid`(화면이 적고 기능이 많을 때), `imageGallery`(화면이 많을 때), `desktopPhones`/`focus`도 쓸 수 있다.

**6. 검사·빌드** — `npm run portfolio:check`(오류 0) → `npm run typecheck` → `npm run build`

**7. PDF** — `npm run portfolio:export -- --slug <slug> --lang all --png`. "잘림 의심"이 나오면 문구를 줄이거나 화면을 나눈다. PNG 몇 장을 직접 열어 본다.

**8. 미리보기·확인** — `node scripts/preview-build.mjs` → CLAUDE.md 방식으로 미리보기 재게시. 목록·메인 Works·상세·출력 화면, 데스크톱 1440·모바일 390, KO/EN/JP를 확인한다(전체 페이지 캡처는 화면 밖 이미지가 비어 보일 수 있으니 의심되면 해당 위치로 스크롤해 확인).

**9. 마무리** — `CHANGELOG.md`의 `[작업 중]`에 한 줄, 커밋(한국어, 무엇을 왜). 새 `pius-work` zip을 주고 프로젝트 파일 교체를 안내한다.

## 수정 요청
- "문구 바꿔줘" → ko·en·ja 함께 / "사진 바꿔줘" → images 교체, 중복 확인
- "공개해줘" → `approved` (번역·사진·pending 오류가 없을 때만)
- "맨 앞으로" → `order` / "크게" → `featured` / "내려줘" → `visible: false`
- 수정 후에도 6~9를 다시 한다.
